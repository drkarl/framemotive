# Requirements and measurable outcomes

**Scope vocabulary:** **M0** is the first application-ready software foundation. **Next** is a near-term library milestone. **Future** requires further design or integration evidence. Requirements are not promises of current functionality.

## Users and jobs

| User job | Desired library result |
| --- | --- |
| Adapt an image or video shot to a new canvas without hiding a known subject | A crop and transform expressed in source and target coordinates, or explicit infeasibility. |
| Reposition graphics and captions around subjects | Layer transforms satisfying safe-area and separation rules, with reported compromises. **Next.** |
| Reframe moving subjects | Bounded trajectory/keyframes across time, with cut-aware smoothing. **Future.** |
| Transfer decisions to an editing application | Versioned, tool-neutral decisions and an adapter that reports unsupported operations. **Future.** |

## M0 functional requirements

| ID | Requirement | Acceptance evidence |
| --- | --- | --- |
| F-01 | Accept source and target canvas dimensions of `1..=65_536` pixels per axis and a single static, full-bleed visual layer with a known source extent. | Valid synthetic landscape, portrait, and square cases construct and validate. |
| F-02 | Represent finite axis-aligned regions of interest in source pixel-edge coordinates, each marked **required** for M0. | Reject NaN, infinities, nonpositive or unrepresentable extents, empty or duplicate IDs, and out-of-bounds required regions with typed diagnostics. |
| F-03 | Compute the largest in-bounds source crop matching the target aspect ratio, subject to containing every required region and optional nonnegative margin. | Crop aspect and source bounds are checked independently; no required region is clipped beyond a documented tolerance. |
| F-04 | When multiple feasible crop positions exist, choose the one whose center is nearest a finite, in-source preferred focus point; otherwise use the source center. | Same input and algorithm version yield the same decision and canonical ordering. |
| F-05 | Return a structured, editable decision: source crop, target rectangle, uniform scale, translation, satisfied constraints, and diagnostics. | A test reconstructs the target transform from the crop and checks it covers the target canvas. No raster output is needed. |
| F-06 | Report invalid input and mathematically infeasible required visibility separately; never label either as a solved adaptation. | Synthetic fixtures cover region wider/taller than any target-aspect crop, a valid margin extending outside the source (`Infeasible`), and malformed geometry (`InvalidInput`). |
| F-07 | Provide a library API and one runnable synthetic example. | Example output is generated by real code and checked in tests; README lists only implemented behavior. |

M0 treats the crop as **full bleed**, with no padding or letterboxing. It accepts only one visual layer and static geometry. A required ROI may be a title or subject region baked into that media. Caller-supplied importance is trusted; there is no detection model. If preserving all required content needs letterboxing, a different composition, or a wider crop, M0 reports infeasible.

## Next functional requirements

- For a single static source layer, distinguish hard visibility from soft framing preferences with explicit priorities, penalties, and measured violations; never silently downgrade hard requirements.
- Define the constraint vocabulary and result schema so a later layer model can add safe rectangles, layer bounds, and pairwise separation without changing the meaning of existing constraints.
- Produce multiple target decisions from one source specification without mutating it.
- Provide deterministic ranking and a declared tie-break policy for alternative solutions.
- Define a versioned, machine-readable interchange document only after consumers and compatibility tests are identified.

Movable independent overlays, collision avoidance, safe-area placement, and separation solving belong to M2. M2 extends hard/soft semantics to layer placement: hard limits cannot be silently relaxed, while soft violations need measured costs. Collision and unsafe-placement diagnostics need actual layer geometry to measure.

## Future functional requirements

- A future subject-track input contract: caller-supplied stable track IDs, source-space bounds or points at rational times, media timebase, cut boundaries, observation gaps, and explicit confidence/provenance where available. Missing samples must not silently imply continuous visibility.
- Cut-aware smoothing, velocity and acceleration limits, between-sample visibility checks, and editable keyframe reduction over those tracks. Spans without a justified interpolation or visibility bound must be reported as unverified.
- Crop/pad/letterbox alternatives, multiple candidate regions, masked and rotated content, animated text and captions, and ranked alternative compositions.
- Adapter contracts that report `supported`, `approximated`, `unsupported`, or `unverified` operations and verify a saved project where an editor exposes that capability.

## Nonfunctional requirements

| ID | Requirement | M0 measure or later gate |
| --- | --- | --- |
| N-01 | Deterministic behavior | Stable diagnostic ordering, algorithm version and tie-break rules; repeated M0 typed decisions compare equal under the same build/target. Cross-architecture bitwise equality is not yet promised. |
| N-02 | Numerical safety | Reject nonfinite values; positive representable extents; bounded conversions; test near-edge and small/large supported canvases. Use the source/target pixel tolerance proposed in ADR-002 for post-computation checks, never for input validity. |
| N-03 | Explicit outcomes | M0 emits `solved`, `invalid_input`, or model-scoped `infeasible`; `unsupported` and `indeterminate` are reserved for later request/solver models. A timeout is not an infeasibility proof. |
| N-04 | Performance | M0 geometry should be O(number of required regions); measure a 1,000-region synthetic case and record machine/build before declaring a latency target. Later solver budgets are per problem class. |
| N-05 | Portability | Stable Rust; Linux, macOS, Windows CI planned before release. No native optimizer dependency in M0. |
| N-06 | Testability | Synthetic fixtures, unit and integration tests, geometric invariants, and a bounded property-test plan. No project-specific media assets. |
| N-07 | API stability | Pre-1.0 semver; avoid treating an example JSON shape as a committed exchange standard. Changes require a decision record and migration note once external consumers exist. |
| N-08 | Dependency hygiene | Minimum dependencies; licences and transitive native build requirements checked before adding solver or editor adapters. |

## Explicit non-goals for M0

Rendering, encoding, media decoding, subject detection, AI inference, image saliency, creative judgment, multi-layer solving, animation, frame timing, editor integration, and general timeline representation.

## Decision gates

1. Does the M0 operation solve a real, independently useful crop problem better than a simple center crop by preserving caller-marked regions?
2. Immediately after a stable M0 crop decision exists, can a minimal adapter translate it into one editor's editable crop/transform fields, save and reopen the project, and verify the persisted operation? This is an early experiment, not an M0 integration requirement.
3. What numeric tolerance and canvas bounds are safe for the first stable API?
4. Do actual multi-layer cases justify a linear/Cassowary, MILP/CP, heuristic, or hybrid backend?
